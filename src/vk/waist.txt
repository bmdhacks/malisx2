# The Vulkan waist: every entry point name in the r44p1 blob's proc-address
# table plus the loader-only Android hooks, with its class (regenerated
# from its waist.json, 2026-09-28). gen_waist_stubs.py turns this list into
# the stub entry points that fill whatever the driver and Mesa's common
# entry points leave empty.
#
#   a  loader-required        implement
#   b  called by ARMSX2       implement
#   c  out of the waist, void       stub: log and skip; abort in a
#                                   measurement build
#   d  out of the waist, returns a value
#                                   stub: log, return the waist error
#                                   (VkResult) or 0
#
# A stub is generated for every name here, whatever its class: an a/b
# entry point that is not implemented yet behaves like c/d until it is.
# The class says who calls the command (the loader, ARMSX2, nobody), not
# whether a back half implements it: vkCmdDispatchIndirect and
# vkUpdateDescriptorSetWithTemplate stay c although every architecture
# implements them.
# "nonnull" marks the 49 out-of-waist names that must resolve because the
# Android loader or ARMSX2 requires a non-NULL pointer; every name here
# resolves anyway.
#
# "noregistry" marks a name that is not in Mesa's vk.xml, so Mesa's
# dispatch tables have no slot for it and no stub is generated:
# vkGetSwapchainGrallocUsage3ANDROID exists only in Android's
# vk_android_native_buffer.h. The Android loader uses the highest-numbered
# gralloc-usage hook a driver exposes, so implementing ...Usage2ANDROID
# (in the registry) is enough; that is the Android WSI choice.
# vkCmdSetLogicOp and vkCmdSetPatchControlPoints are rows of the blob's
# table without the EXT suffix that no Vulkan version defines; nothing can
# ask for them by a registry name, and their EXT forms are stubbed.
#
# Aliases (vkFooKHR next to vkFoo) share one stub with their core name.

# Forward targets of Mesa's common entry points. Mesa implements a number of
# commands as a function that builds a *2 / *3 form of the same command and
# calls it through the device's dispatch table (vk_common_CmdDrawIndirect
# calls vkCmdDrawIndirect2KHR). When a back half neither implements the
# command nor the *2 form, Mesa's function is what the table holds and the
# call ends in a NULL slot. These are the *2 forms that no back half
# implements, so that the call ends in a stub that logs it (aborts in a
# measurement build) instead. A host test reads the forwards out of Mesa's
# sources and checks that the target of each one that is in effect resolves,
# so a Mesa update that adds a forward fails it until the target is listed
# here or implemented.
# vkCmdDispatchIndirect2KHR is not here: every back half implements
# vkCmdDispatchIndirect itself, so Mesa's forward to it is never in effect
# (the same test checks that).
